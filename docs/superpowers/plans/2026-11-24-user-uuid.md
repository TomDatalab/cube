# Users Keyed by a UUID Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user's key becomes a UUID everywhere (database, SpiceDB, tokens, API `id`). The username becomes a unique, renamable attribute, and nothing that works today breaks.

**Architecture:**
- An idempotent database migration gives every user a UUID `id` and a `username` column.
- A one-time boot migration rewrites SpiceDB subjects from `user:<username>` to `user:<uuid>`.
- Identity resolves token subjects by UUID, then by username (legacy tokens).
- Every API path naming a user accepts either key.
- The Playground shows usernames and calls the API with ids.

**Tech Stack:** Rust (axum, tokio-postgres, SpiceDB HTTP), React/TS Playground (vitest).

**Spec:** `docs/superpowers/specs/2026-11-24-user-uuid-design.md`

## Global Constraints

- `users.id` holds the user's UUID (as text, lower-case hyphenated). `users.username` is `text NOT NULL UNIQUE` and validated by today's `validate_user_id` rules (the existing username format).
- **Nothing that works today breaks:**
  - Every user keeps exactly their SpiceDB relationships.
  - A token whose `sub` is a username still authenticates (until `exp`), with `iat` still checked against `password_changed_at`.
  - API paths and the create body field `id` that name a user by username keep working.
- **SpiceDB user relations:**
  - The ones to migrate: `platform#admin`, `organization#owner`, `organization#member`, `workspace#owner`, `workspace#editor`, `workspace#viewer`, `rule#member`.
  - `role#can_*@user:*` is untouched.
- **Migrations:** both migrations are idempotent, and each records a marker when complete. The SpiceDB one logs every relationship it rewrites (`tracing::info!`).
- **Unchanged:**
  - `CUBE_RBAC_ADMINS` lists usernames.
  - `created_by` and `updated_by` columns store the acting user's username as text.
- **API shapes:**
  - A user object is `{id, username, name, email, disabled, createdAt}`.
  - Member, owner and rule-member entries carry `user` (the UUID) and `username`.
  - The login answer's `user` has `id` (the UUID) and `username`.
- **Running the tests:**
  - Integration tests need `CUBE_TEST_PG_URL`. Build it from `/root/cube-rust/.env` `CUBE_APP_DB_URL` with `/cube_app` → `/postgres`.
  - Run them in a clean env: `env -i PATH="$PATH" HOME="$HOME" CUBE_TEST_PG_URL=...`.
  - Lib tests: `env -u CUBE_APP_DB_URL`.
  - Never print secrets.
  - No workspace-wide `cargo fmt`.

## Review Focus

- A user created before the migration logs in with their username, keeps every workspace, organization and rule they had, and their old token still works.
- Renaming a user: they log in with the new name and keep their access. The old name is free for a new user. Paths by the old name now 404.
- The migration runs twice (a restart): no duplicate or lost relationship, and no error.
- A username that looks like a UUID cannot be created (it would make path resolution ambiguous). Lookups try UUID first.
- `CUBE_RBAC_ADMINS` names a user created before the migration: they are still a platform admin after it.

### Task 1: Database: users get a UUID id and a username column

**Files:**
- Modify: `rust/cube/cubeserver/src/rbac/migrations.sql`, `rust/cube/cubeserver/src/rbac/store.rs`
- Test: `rust/cube/cubeserver/tests/rbac_store.rs`

**Interfaces (produces):**
- `User` gains `pub username: String`; `User.id` is the UUID string.
- `NewUser` takes `username` (no caller-chosen id); `create_user` generates the UUID.
- `Store::user(id)` looks up by UUID.
- `Store::user_by_username(&str) -> Result<Option<User>, StoreError>`.
- `Store::resolve_user(key: &str) -> Result<Option<User>, StoreError>`: tries the UUID when `key` parses as one, else the username.
- `update_user` can change `username`: a unique violation → `StoreError` Conflict.
- `search_users` matches username, name and email.

**Steps:**
- [ ] **Step 1: Failing tests** in `tests/rbac_store.rs`:
  - `a_new_user_gets_a_uuid_and_keeps_its_username`
  - `resolve_user_takes_a_uuid_or_a_username`
  - `renaming_a_username_keeps_the_id_and_frees_the_old_name`
  - `a_username_shaped_like_a_uuid_is_refused`
  - `the_migration_keys_existing_users_by_uuid_once`. This one runs the migration on a database holding a legacy row (`id = 'ann'`, no username) plus a `user_attributes` row, runs it again, and asserts:
    - `username = 'ann'`, and `id` parses as a UUID that is unchanged on the second run;
    - the attributes follow the new id.
- [ ] **Step 2:** Run them and confirm they fail.
- [ ] **Step 3: Implement.**
  - Migration: a marker table `rbac_migrations (name text PRIMARY KEY, applied_at timestamptz NOT NULL DEFAULT now())`.
  - A guarded step `users_uuid`, done in one transaction:
    - add `username`, backfill it from `id`, make it NOT NULL UNIQUE;
    - make the `user_attributes` FK `ON UPDATE CASCADE`;
    - set `id = gen_random_uuid()::text` where `id` is not a UUID;
    - insert the marker.
  - Fresh databases end in the same shape.
- [ ] **Step 4:** Run `--test rbac_store` and `--lib`; both must pass.
- [ ] **Step 5: Commit** `feat(rbac): users are keyed by a UUID, the username is a column`.
